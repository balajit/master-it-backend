Recommended Backend Changes
Critical (blocking any integration)
R1 — Register v1 routes in the OpenAPI spec.
All /api/v1/* routes exist but don't appear in the spec. Run npx openapi-typescript after fixing this; it will expose UnitResponse, SectionResponse, LessonResponse, PracticeResponse, and GoalResponse to the frontend.
R2 — Add GET /api/courses/{course_id}/units to the spec.
The study page navigates from course_id (URL param) → unit_id → unit detail. This bridging endpoint exists but is invisible to the frontend.
Schema Additions
R3 — Add status: ProgressStatus to GoalResponse.
Currently GoalResponse has score and completed_at only. A computed status is needed for PracticeCard.
R4 — Add description: str to GoalResponse.
PracticeCard needs a description string for quiz/checkpoint items. Currently absent.
R5 — Add activity_type: str to PracticeResponse and GoalResponse.
Values like "quiz", "practice", "project", "self_test" are needed for the badge prop on PracticeCard.
R6 — Add locked: bool to PracticeResponse and GoalResponse.
The backend LOCKED state exists but isn't surfaced on these response models. Drives PracticeCard.disabled.
R7 — Differentiate about from description in UnitResponse.
Both fields currently return the same string. InfoCard needs a richer body copy distinct from the short description used in listings.
Standardization
R8 — Normalize ProgressStatus casing.
The v1 routes return MASTERED, PRACTICED, etc. (uppercase). The frontend statusConfig.ts uses lowercase. Pick one convention. Lowercase is preferred since the frontend already uses it and JSON conventions favor it.
R9 — Add progress_label: str to PracticeResponse.
Compute server-side from required_correct and total_questions (e.g. "Score 12/15 to pass"). Avoids duplicating formatting logic in the client.
R10 — Add action_label: str to PracticeResponse and GoalResponse.
Derive from (status, activity_type) server-side (e.g. "Start Quiz", "Continue", "Review"). Centralizes UX copy logic.
